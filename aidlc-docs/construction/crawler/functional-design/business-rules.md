# Business Rules

## BR-1: 중복 감지 규칙

| 규칙 | 설명 |
|------|------|
| BR-1.1 | 공고 고유번호(seq)가 DB에 이미 존재하면 **신규 저장하지 않음** |
| BR-1.2 | seq는 SH 게시판의 게시글 번호에서 추출 (URL 또는 HTML 속성) |
| BR-1.3 | seq는 Announcement 컬렉션에 unique index로 설정 |

---

## BR-2: 공고 상태 전이 규칙

```
[크롤링 시 감지된 상태]          [DB 상태 전이]
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
신규 공고 (접수 전)         →   status: "예정"
신규 공고 (접수 중)         →   status: "진행중"
기존 공고 (접수 마감)       →   status: "마감" (업데이트)
기존 공고 (상태 변경 없음)  →   변경 없음
```

### 상태 판단 기준
- **"예정"**: application_start가 미래 날짜이거나 아직 접수 시작 전
- **"진행중"**: 현재 날짜가 application_start ~ application_end 사이
- **"마감"**: application_end가 과거 날짜이거나 게시판에서 마감 표시

### 상태 전이 다이어그램

```
예정 ──→ 진행중 ──→ 마감
```

- 역방향 전이 없음 (마감 → 진행중 불가)
- "마감" 상태의 공고는 활성 목록 API에서 제외

## BR-3: 크롤링 대상 필터링 규칙

| 규칙 | 설명 |
|------|------|
| BR-3.1 | 게시판 목록에서 status가 "공지"인 항목은 **수집하지 않음** |
| BR-3.2 | 게시판 목록에서 status가 "마감"인 항목은 **기존 공고 상태 업데이트용으로만 사용** |
| BR-3.3 | 분양 게시판만 크롤링 (board = "분양") |

---

## BR-4: PDF 처리 규칙

| 규칙 | 설명 |
|------|------|
| BR-4.1 | 상세 페이지에서 PDF 확장자(.pdf) 링크만 추출 |
| BR-4.2 | PDF를 S3에 업로드 시 키 패턴: `announcements/{seq}/{원본파일명}` |
| BR-4.3 | PDF 업로드 성공 시 analysis_status를 "pending"으로 설정 |
| BR-4.4 | PDF 업로드 실패 시 analysis_status를 "failed"로 설정 |
| BR-4.5 | PDF가 없는 공고도 저장하되, analysis_status는 "pending" 유지 (수동 확인 대상) |

---

## BR-5: 스케줄링 규칙

| 규칙 | 설명 |
|------|------|
| BR-5.1 | 12시간(43,200,000ms) 간격으로 자동 실행 |
| BR-5.2 | 수동 트리거(POST /api/worker/trigger)로도 즉시 실행 가능 |
| BR-5.3 | 동시에 2개 이상의 크롤링이 실행되지 않도록 락(lock) 또는 상태 체크 |
| BR-5.4 | 이전 크롤링이 진행 중이면 수동 트리거 시 "이미 실행 중" 응답 반환 |

---

## BR-6: 요청 제한 규칙 (Rate Limiting)

| 규칙 | 설명 |
|------|------|
| BR-6.1 | HTTP 요청 간 최소 1초 딜레이 |
| BR-6.2 | 요청 타임아웃: 30초 |
| BR-6.3 | User-Agent 헤더 설정 (봇 식별 가능하도록) |

---

## BR-7: 데이터 유효성 규칙

| 규칙 | 설명 |
|------|------|
| BR-7.1 | seq는 비어있을 수 없음 (필수) |
| BR-7.2 | title은 비어있을 수 없음 (필수) |
| BR-7.3 | detail_url은 유효한 URL 형식이어야 함 |
| BR-7.4 | application_start/end는 YYYY-MM-DD 형식 또는 null |
| BR-7.5 | 파싱 실패한 필드는 null로 저장 (전체 공고 저장 실패시키지 않음) |
